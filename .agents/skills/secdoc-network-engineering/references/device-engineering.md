# Device Engineering

Contents: routers · switches · firewalls · wireless controllers and APs · load balancers · VPN gateways · management-plane hardening · configuration lifecycle · out-of-band management. Command syntax names its platform; behaviors that differ by vendor say so.

## Routers

**Interfaces and subinterfaces.** A routed interface carries one L3 network; 802.1Q subinterfaces (router-on-a-stick) carry one per tag — IOS-XE: `interface Gi0/0/1.10` / `encapsulation dot1q 10` / then the address. The gotcha set: the physical interface needs no IP but must be up; native-VLAN traffic arrives untagged (match it with `encapsulation dot1q 1 native` or lose it); and a router-on-a-stick's uplink is the aggregate bottleneck for all inter-VLAN traffic — fine for labs and branch edges, replaced by SVIs on L3 switches anywhere volume matters.

**Routing-protocol deployment specifics** — the difference between "OSPF is on" and "OSPF is engineered":

- **Authentication** on every adjacency. OSPF: MD5 historically, SHA via key chains on modern IOS-XE/Junos (RFC 5709); EIGRP and BGP take key chains / MD5 (BGP: TCP-AO, RFC 5925, where both ends support it — flag currency). Unauthenticated IGPs accept adjacency from anything on the segment; that is a route-injection invitation.
- **Passive interfaces** by default (`passive-interface default`, then `no passive-interface` on real transit links). User-facing segments should hear no hellos and offer no adjacency.
- **Route filtering**: prefix lists for "which prefixes" (match on prefix + length range — `ip prefix-list DENY-LONG seq 5 permit 10.0.0.0/8 le 24`), route maps for "which prefixes AND what to do to them" (match + set: communities, metrics, tags, next hops). Distribute lists are the blunt legacy tool. Filter at every redistribution point and every eBGP session — an unfiltered eBGP customer session is how full tables leak and how you become a transit AS by accident (filter outbound to your own prefixes; RPKI origin validation inbound where supported).
- **Policy-based routing** overrides the routing table per traffic class (route-map matching an ACL, setting a next hop, applied to the ingress interface). Legitimate for "guest traffic exits the cheap circuit"; a maintenance liability everywhere else because it's invisible to routing-table troubleshooting — document every PBR instance in the design doc or watch someone chase a ghost.

**Control-plane protection.** The data plane forwards in hardware; punting to the CPU (mgmt traffic, TTL-expired, options, ARP, routing protocols) is the exhaustible resource. CoPP (Control Plane Policing) classifies and rate-limits punted traffic — IOS-XE `control-plane` / `service-policy input COPP`. Without it, a traceroute storm or a scanning worm can starve the very routing protocols keeping the box reachable.

**Platform behaviors that bite:**

- **CEF** (and its equivalents — all modern platforms forward from a precomputed FIB + adjacency table, not the RIB). Consequences: `show ip route` is what the control plane believes, `show ip cef` is what the forwarding plane does — troubleshoot forwarding with the second; and process-switched exceptions (options, fragmentation needed, some tunnel cases) hit the CPU, which is why "the router is slow only for some traffic" is a punt-path question.
- **MTU and fragmentation.** Interface MTU, IP MTU, and MPLS/tunnel overhead are separate knobs; a GRE or IPsec tunnel silently costs 24–80+ bytes. On tunnel heads, clamp TCP MSS (`ip tcp adjust-mss 1360` for GRE/IPsec over 1500) — it prevents the PMTUD-black-hole class of tickets at the handshake instead of debugging them per-flow.
- **Asymmetric routing** is legal at L3 and fatal through anything stateful (firewalls, NAT). With ECMP or dual exits, either pin flows (route metrics, PBR) or ensure state sync on the stateful pair. "Works from here, fails from there" with a firewall in one direction's path is this, almost every time.

## Switches

**VLANs and trunking.** 802.1Q inserts a 4-byte tag; the **native VLAN** goes untagged on the trunk — mismatched native VLANs merge two broadcast domains silently (CDP complains, users suffer). Engineering standard: set the native VLAN to an unused, dedicated VLAN, don't put users in it, or tag it outright (`vlan dot1q tag native`). Prune trunks to needed VLANs (`switchport trunk allowed vlan 10,20,30`); disable DTP negotiation on every port (`switchport nonegotiate`, mode set explicitly to access or trunk) — DTP-negotiated trunks from an attacker's box is VLAN hopping method one; native-VLAN double-tagging is method two, killed by the native-VLAN discipline above. **VTP**: a protocol that propagates VLAN databases, and whose failure mode — a higher-revision switch (a lab box, a returned RMA) overwriting the domain's VLAN database and deleting every VLAN in production — has earned it a standing recommendation: transparent mode or off (VTP off / use v3 with a single primary if you must). The convenience is not worth the blast radius.

**Advanced spanning-tree operations** (mechanics in topology-design.md; these are the device knobs):

- **PortFast** on all host ports (skip listening/learning; DHCP works on first link-up) — always paired with **BPDU guard** (err-disable the port if a BPDU arrives: a host port receiving BPDUs means an unmanaged switch or a bridge loop being born).
- **Root guard** on ports facing anything that must never become root (toward access, toward third parties) — superior BPDUs put the port in root-inconsistent instead of moving your root.
- **Loop guard** (or Cisco's UDLD, or both) on trunks: a blocked port that stops hearing BPDUs assumes the path died and unblocks — on a unidirectional fiber that assumption creates the loop. Loop guard holds it loop-inconsistent instead.
- Err-disabled ports stay down until manual `shutdown`/`no shutdown` or `errdisable recovery` — decide the recovery policy deliberately; auto-recovery on BPDU guard re-arms the loop every N seconds.

**EtherChannel/LACP.** Bundle rules: matching speed/duplex/VLAN config on every member, LACP (`channel-group N mode active`) over static `on` (LACP detects miswiring and one-way links; static bundles forward into the fault). Configure the port-channel interface, not members — member-level drift is the classic "why is VLAN 30 broken on half the flows" (per-flow hashing means a misconfigured member breaks a deterministic subset of flows, the signature to recognize). Verify hash distribution (`show etherchannel load-balance`) matches traffic reality — src-MAC hashing behind a router polarizes onto one link.

**Layer 3 switching and SVIs.** An SVI (`interface Vlan10`) is the VLAN's routed gateway on the switch — inter-VLAN routing in hardware, the replacement for router-on-a-stick. SVI is up when the VLAN exists and has at least one up port (autostate); routed ports (`no switchport`) for point-to-point L3 links between switches. The design decision it enables: L3 at the access layer (each closet routes, no spanned VLANs, no STP blocking, ECMP uplinks) versus L2 access (VLANs span to distribution, FHRP + STP alignment required) — L3 access trades VLAN mobility for a smaller failure domain and is winning where wireless made wired mobility moot.

**Stacking and virtual chassis.** One control plane over multiple physical switches (StackWise, Virtual Chassis, VSS/StackWise Virtual across distribution pairs): one config, cross-member EtherChannel, no FHRP needed. Costs: a control-plane bug or a botched upgrade takes the whole stack; stack cables/merge behavior and split-brain need explicit understanding before, not during, the first incident; upgrades want the platform's ISSU story verified rather than assumed.

**PoE budgeting.** Per-port class (802.3af 15.4 W, 802.3at 30 W, 802.3bt up to 60/90 W at the PSE) against the switch's total PoE budget — a 48-port switch rarely powers 48 bt-class loads. Sum the actual device draws (APs and cameras publish them), add headroom, check the budget per power-supply-failure scenario if PSUs are redundant. Brownouts from oversubscribed PoE present as "random device reboots," not as a clean error.

**Access-layer security feature set** — deployed together, they close the on-link attack class:

- **Port security**: cap MAC count per port (violation shutdown/restrict), kills MAC-flooding CAM exhaustion.
- **DHCP snooping**: switch marks trusted ports (toward the real server); Offers from untrusted ports drop. Builds the binding table (MAC/IP/port/VLAN) the next two features consume.
- **Dynamic ARP inspection**: validates ARP against the snooping binding table — cache poisoning drops at the port.
- **IP Source Guard**: same table, filters spoofed source IPs per port.
- **802.1X/NAC**: port-level authentication (supplicant → switch as authenticator → RADIUS), with MAB fallback for printers and dumb devices, and a guest/quarantine VLAN policy for failures. The deployment reality: monitor mode first, enforce after the exception list is real.
- **Storm control**: per-port broadcast/multicast/unknown-unicast thresholds — the circuit breaker for loops that got past everything above.
- **Private VLANs**: isolated/community ports sharing one subnet and gateway — hosting and hotel-style segments where hosts must not see each other but renumbering is off the table.

## Firewalls (device level)

**Zones and interfaces.** Modern firewalls bind interfaces to zones and write policy zone-to-zone; the engineering here is minimal and structural — interface/zone assignment, routed vs transparent (L2 bump-in-the-wire) mode, VLAN subinterfaces per zone. *Which* zones exist and what the policy allows is architecture: compose with cybersecurity-architecture.

**NAT variants and their pitfalls.**

- **Static NAT**: one-to-one, bidirectional — inbound-reachable servers.
- **Dynamic NAT**: pool-based one-to-one, outbound-initiated, exhausts.
- **PAT/NAPT** ("overload"): many-to-one on ports — the default for user egress; per-IP port capacity (~64k sessions minus reserved) is the exhaustion math for sizing, and some protocols embed addresses in payloads and break without ALGs (SIP, active FTP) — and break differently *with* buggy ALGs, which is why "disable the SIP ALG" is tribal wisdom on several platforms.
- **NAT traversal**: IPsec through PAT needs NAT-T (UDP 4500 encapsulation, negotiated in IKE); hairpin/reflection (inside host → public IP of inside server) needs explicit support or split DNS; and NAT order-of-operations vs routing and VPN interesting-traffic matching differs per platform (Cisco ASA/FTD, PAN-OS, FortiOS each sequence NAT and policy lookup differently) — never assume, check the vendor's packet-flow diagram.

**Rulebase mechanics and hygiene.** First-match top-down evaluation on every mainstream platform. Standing rules: specific above general; an explicit cleanup deny-log at the bottom (the implicit deny doesn't log on all platforms, and the log is the point); detect **shadowed rules** (a broader earlier rule making a later one unreachable — policy-analysis tooling or periodic manual audit); every rule commented with owner/ticket/date; objects and groups instead of literal addresses (one edit, every rule); scheduled recertification because rulebases only ever grow — the 4,000-rule firewall nobody understands started as a clean 40.

**HA pair design.** Active/passive: one forwards, state (session table, and optionally config) syncs to the peer over a dedicated HA link; failover triggers on interface/path monitors and hellos. Active/active: both forward (per-VLAN, per-VSYS, or clustered) — buys throughput, costs asymmetric-flow handling and split-brain complexity; the honest default is active/passive sized so one box carries everything, because an active/active pair that can't run on one member isn't HA, it's load sharing with a failure amplifier. Engineering rules: dedicated HA interfaces (never through the production path), preemption decided deliberately (auto-preempt flaps back into a still-sick box), and **failover tested on schedule** — pull the cable in a change window; an HA pair whose failover was never exercised has an unknown failover behavior, which is to say none.

**Performance realities.** Datasheet throughput is large-packet, features-off. The numbers that size a firewall: threat-inspection throughput (commonly 3–10× lower than raw), new sessions/second, concurrent session table size, and **TLS-inspection cost** — decrypting and re-encrypting can halve inspected throughput again and requires the certificate-trust deployment (internal CA pushed to endpoints) plus a bypass list for pinned/regulated traffic. Size on the inspected numbers for your enabled feature set at your real packet mix, then add growth; a firewall bought on the datasheet number is undersized on arrival.

## Other endpoints

**Wireless controllers and APs.** Controller-based (WLC, physical/virtual/cloud): APs tunnel (CAPWAP) or locally switch traffic, controller owns RF (channel/power assignment), roaming (fast-roaming standards 802.11r/k/v), and policy; controllerless/distributed shifts that into AP clusters — the trade is scale and feature depth vs boxes and licensing. Roaming works when the SSID/security config is identical everywhere and the client can find a better AP before losing the current one — which is an RF design fact: overlapping cells at −67 dBm-ish edges, adjacent APs on non-overlapping channels (2.4 GHz: 1/6/11 only; 5/6 GHz: plan by DFS and width), power turned *down* to shrink cells rather than up to shout. AP placement decisions need that much RF and no more; a proper survey (predictive then validated) is the deliverable for anything beyond a small office.

**Load balancers.** L4 (transport): forwards on IP/port, fast, application-blind. L7 (application): terminates the client connection, reads HTTP/TLS, routes on host/path/header, rewrites — required for anything content-aware, costs TLS termination CPU and adds the LB as an application-layer actor (it has its own timeouts, buffering, header behaviors to engineer). **Health checks** define failover truth: check the actual service (an HTTP 200 from the app path, not a TCP SYN to the port — a wedged app answers SYNs for hours), with intervals/thresholds tuned so detection beats user complaints without flapping on GC pauses. **Persistence** (source-IP or cookie) pins clients to servers for stateful apps — cookie-based survives NAT'd client populations, source-IP doesn't. Topologies: inline (LB is the default gateway both ways — simple, symmetric) vs one-arm (LB on a stick, requiring SNAT so return traffic comes back through it — which hides client IPs from servers unless X-Forwarded-For is engineered end to end).

**VPN gateways.** Site-to-site IPsec: IKE negotiates (IKEv2 unless the peer can't — simpler exchanges, built-in NAT-T and liveness, EAP support), phase 1 protects the negotiation, phase 2 (child SAs) protects traffic. Crypto selection in 2026: AES-GCM (combined mode), SHA-2 family, DH group 14 minimum / ECDH 19–21 preferred, PFS on; DES/3DES/MD5/SHA-1/group 2 refused, not deprecated-but-accepted. **Common interop failures**, in observed frequency order: mismatched phase 2 selectors/proxy-IDs (policy-based peer vs route-based peer — VTI/route-based on both ends avoids the whole class), mismatched PFS or lifetimes (tunnel establishes, dies at rekey — the "drops every hour" signature), NAT between peers without NAT-T, and fragmentation of large IKE certificates (enable IKE fragmentation). Remote access: IKEv2 or TLS-based termination, MFA against the AAA backend, split- vs full-tunnel decided as policy (compose with the architecture skills), and the device-level part — session capacity, address-pool sizing, and pushing routes/DNS correctly.

## Cross-cutting device disciplines

**Management-plane hardening**, the same checklist on every device class:

- SSH only (v2, modern KEX — retire CBC/SHA-1 kex on old images), Telnet/HTTP absent, not merely unused; management ACLs restricting sources to the management networks.
- **AAA**: authentication and command authorization against TACACS+ (per-command authorization and full command accounting — the audit trail) or RADIUS (802.1X's native protocol; coarser device-admin authorization); local fallback account for AAA-server-unreachable, with a vaulted password, tested.
- Role-based access: read-only for NOC/monitoring, netadmin separated from security-admin where the platform supports it.
- **SNMPv3** authPriv only (v2c communities are cleartext credentials); views restricting OID trees; traps/informs to the NMS.
- **NTP with authentication** — accurate, trusted time or the logs cannot be correlated and the certificates misbehave; at least two sources, stratum-sane.
- **Central syslog** at an informational-or-better severity, with local buffer as the crash record; timestamps in one timezone (UTC) across the estate.
- Login banners (legal), exec timeouts, password/secret hashing at the platform's strongest (type 8/9 on IOS-XE, never type 7 — type 7 is encoding, not encryption).

**Configuration lifecycle.** Automated config backup on change and on schedule, to a system that diffs (RANCID/Oxidized-class or the vendor controller); every change through a window with a written rollback that was actually verified to exist (`copy run start` before, config archive/rollback features where the platform has them — IOS-XE `configure replace`, Junos `commit confirmed` which auto-reverts if you don't confirm, the single best safety feature in network CLI design and worth naming to students). **Firmware/OS upgrades**: run a target-version standard (typically the vendor's recommended/gold release, not latest), read the release notes' open caveats against your feature set, upgrade lab/low-risk first, schedule around the platform's real reload time, and stage the rollback image on the device before starting. Unpatched network devices are the perimeter breach class of the last several years — upgrade cadence is a security control, not housekeeping.

**Out-of-band management** — the discipline that saves you when in-band is down: console servers (serial, over a path that shares nothing with production — separate switch, separate circuit, cellular where the budget allows), management interfaces in a dedicated OOB network/VRF so a routing mistake can't orphan management, and power control (switched PDUs) reachable the same way. The test: assume the core is down and every trunk is dark — can you still reach the console of everything you'd need to fix it? If the OOB path traverses the network it manages, it's decoration. Build it before the incident; it cannot be built during one.
