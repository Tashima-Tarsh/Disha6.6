# Data Security & Cryptography Architecture

## Scope

This domain covers the architecture of data protection: classification and lifecycle, encryption architecture across states, key management, DLP, tokenization and masking, privacy-enhancing patterns, and post-quantum readiness. Boundary with neighbors: identity decides *who* reaches data (`domain-iam.md`); this file decides how data is classified, protected, and destroyed wherever it lands. TLS as network policy (inspection, termination points) composes with `domain-network-perimeter.md`; cloud KMS platform specifics with `domain-cloud-hybrid.md`; regime obligations (GDPR, PCI) with `compliance.md`.

## Architecture patterns

**Data classification — the load-bearing, most-skipped foundation.** Every downstream control in this domain keys off classification: encryption requirements, DLP policy, retention, access tiers, DPIA triggers. And most organizations either have no scheme or a five-level scheme nobody applies. The architecture that works: **3–4 levels maximum** (public / internal / confidential / restricted is plenty — granularity beyond what people can apply from memory is granularity that won't be applied), definitions written as *examples* ("customer PAN, health records, CUI → restricted") rather than abstractions, regulated categories (PII/cardholder/CUI/PHI) mapped explicitly to levels, and labels applied **by default and by automation** — classification at creation via templates and location inheritance ("everything in this repository/share/bucket is confidential"), automated pattern-based discovery for the legacy estate, and manual labeling only as the exception path. A classification policy without an application mechanism is a shelf document; assess the mechanism, not the policy.

**Data lifecycle architecture.** Four stages that each need an owner and a mechanism:
- **Discovery** — you cannot protect inventory you don't have; automated discovery (structured stores, file shares, SaaS, object storage) producing a data map — which becomes the input for PCI scoping, GDPR records of processing (Art. 30), CUI boundary definition, and IR's "whose data was it" question (`domain-secops.md`).
- **Labeling** — persistent labels traveling with the object (document metadata, storage tags, column-level tags in the warehouse) so downstream controls (DLP, access, retention) can key off them mechanically.
- **Retention** — schedules per data category driven by the union of regulatory floors and business need, with the architecture bias toward *shorter*: data past its purpose is pure liability (GDPR storage limitation makes this a legal obligation, not just hygiene — `compliance.md`).
- **Defensible deletion** — deletion that actually happens and can be evidenced: automated expiry where the platform supports it, crypto-shredding (destroy the key, and everything under it is unrecoverable) for backup/archive tiers where physical deletion is impractical, and the honest inventory of where deletion *can't* currently reach (that inventory is a findings list).

**Encryption architecture, by state.**
- **At rest** — the layered decision: full-disk/volume encryption defeats physical theft only; storage-service/database-level (TDE-class) defeats media and some infrastructure compromise but is transparent to any authenticated query; application/field-level encryption defeats database compromise and the DBA, at the cost of searchability, indexing, and real development work. Choose per threat: "encrypted at rest" satisfying a checkbox with volume encryption while the threat is SQL injection is the classic mismatch — name which layer defends against which adversary in the design doc.
- **In transit** — TLS posture as policy: current protocol versions per SP 800-52 guidance (verify current revision and minimum-version guidance), certificate lifecycle automated (expiry outages are self-inflicted incidents; shrinking maximum certificate lifetimes make manual renewal untenable — verify current CA/Browser Forum limits), internal traffic encrypted too (the flat-internal-plaintext estate fails the assume-breach test), and mTLS for service-to-service where workload identity supports it.
- **In use** — orientation depth: confidential computing (TEE/enclave-based processing) has matured for specific patterns (processing regulated data on infrastructure you don't fully trust, multi-party computation on shared data); treat as a targeted tool for named use cases, not an estate-wide posture.

**Key management — the real problem.** Encryption is easy; custody is the architecture. The questions that structure the design:
- **KMS/HSM patterns** — cloud-native KMS (cheap, integrated, keys under the provider's root of trust), customer-managed keys within cloud KMS (rotation and policy control, provider still operates the module), external/HSM-backed key origination (BYOK/HYOK-class patterns) where regulation or trust posture demands custody separation from the processing provider, and on-prem HSM (FIPS 140-3 validated — verify module certificate currency) for the top tier. Each step up buys custody at operational cost; match the tier to the data classification rather than defaulting to maximum everywhere.
- **The who-can-decrypt question** — the design's honest center: enumerate every principal (human and workload) whose access to the key material or the decrypt operation makes ciphertext readable, including the KMS administrators and the provider. If the answer includes "any engineer with production access," the encryption is an availability feature, not a confidentiality control. Key-use authorization is IAM policy (`domain-iam.md`) and deserves the same least-privilege review as data access itself.
- **Rotation and custody separation** — rotation schedules per key class with re-encryption strategy stated (envelope encryption makes rotation cheap — rotate the KEK, not the data); separation of duties between key administrators and data administrators; dual control for root/master key operations; and key inventory with owners — orphaned keys guarding production data are a recoverability incident waiting.
- **SP 800-57** (key management) and **SP 800-131A** (algorithm/strength transitions) as the citation anchors.

**DLP, honestly staged.** DLP fails when deployed as a product instead of a program. The staging that works: (1) discovery-and-monitor mode scoped to the top one or two data categories (PAN, CUI) — learn the real flows first; (2) tune on real traffic — the tuning cost nobody budgets is the program's actual price, measured in analyst time per alert and business exceptions per week; (3) blocking only for high-confidence patterns on high-risk channels (exact-match on known identifiers at email/upload egress), expanding as precision proves out. Channel coverage honesty: endpoint DLP, email/SaaS DLP, and network DLP see different things and TLS/SaaS traffic blinds network DLP without inspection architecture (`domain-network-perimeter.md`, TLS inspection). Label-driven DLP (policies keyed to classification labels rather than pattern-matching alone) is the maturity destination — another reason classification is load-bearing.

**Tokenization and masking, by use case.** **Tokenization** (substitute a surrogate, real value held in a hardened vault or derivable only via HSM) — the PCI scope-reduction workhorse: systems holding only tokens can drop out of CDE scope (`compliance.md`), and format-preserving tokens let legacy systems run unmodified. **Static masking** — irreversible de-identification for non-production environments; production data in dev/test is a standing finding with a masking-shaped remediation. **Dynamic masking** — policy-based redaction at query time by role; access-control convenience, not a hard boundary (the real value exists under the mask — score it accordingly). Choose by whether the use case ever needs the real value back: yes → tokenization; no → static masking; presentation-layer only → dynamic masking.

**Privacy-enhancing patterns, where they've matured.** Pseudonymization (GDPR Art. 32(1)(a) names it — reversible separation of identifiers, key held apart) and k-anonymity-style de-identification for analytics releases are production-grade practice. Differential privacy is real but engineering-intensive — mature in large-scale analytics/telemetry contexts, not a bolt-on. Homomorphic encryption and secure multi-party computation remain narrow-use-case tools; flag as verify-current rather than recommending by reflex. The architect's honest framing: aggregation and access control solve most "privacy-preserving analytics" requirements before the exotic tools enter.

**Post-quantum readiness — verify current.** NIST finalized the first PQC standards in August 2024: **FIPS 203** (ML-KEM, key encapsulation), **FIPS 204** (ML-DSA, signatures), **FIPS 205** (SLH-DSA, hash-based signatures) — and migration guidance, additional algorithm selections, and protocol/library support are actively moving; verify current standard status, deprecation timelines for classical algorithms, and ecosystem support before advising. The architecture work is ready now regardless: **cryptographic inventory** (where every algorithm, key length, protocol version, and certificate lives — you cannot migrate what you haven't mapped; this inventory also pays for itself in ordinary crypto-agility), prioritization by data lifetime (harvest-now-decrypt-later means data confidential beyond ~10 years feels the risk first), and demanding PQC roadmaps from vendors holding your long-lived ciphertext. Crypto-agility — the ability to swap algorithms without redesign — is the durable requirement underneath the PQC event.

## Control mapping

- **SP 800-53 Rev. 5**: SC-28 (protection at rest), SC-8 (transmission confidentiality/integrity), SC-12/SC-13 (key establishment/management and cryptographic protection), SC-17 (PKI certificates), MP-6 (media sanitization — defensible deletion's control home, with SP 800-88 as the method reference), RA-2 (categorization — the classification hook), SI-12 (information retention), PT family for privacy processing.
- **CSF 2.0**: Protect (PR.DS data security category — at rest, in transit, in use), Identify (ID.AM-07/08 — data and its classification as inventory).
- **ATT&CK**: T1552 (Unsecured Credentials — keys count), T1005/T1039/T1530 (data from local system/network share/cloud storage — what classification-driven access limits blunt), T1486 (Data Encrypted for Impact — the adversary's key management; backup/recovery is the counter, Art. 32(1)(c)).
- **Compliance hooks**: PCI DSS Req. 3 (stored account data — 3.4/3.5 rendering PAN unreadable and key management) and Req. 4 (transmission); GDPR Art. 5(1)(c)/(e) minimisation and storage limitation, Art. 32(1)(a) pseudonymisation and encryption, Art. 25 default-minimal — see `compliance.md`; CMMC/800-171 3.8 (media protection) and 3.13.11/3.13.16 (CUI cryptography — FIPS-validated modules required, a frequent assessment failure); SOC 2 CC6.1/CC6.7 and the Confidentiality category.

## Decision criteria

- **Small org**: platform defaults on (managed-service encryption, native KMS), classification at 3 levels enforced by storage location, retention via platform lifecycle policies, no DLP until there's someone to tune it — location discipline and access control first.
- **Mid-size**: customer-managed keys for the restricted tier, data discovery tooling, static masking into non-production, DLP in monitor mode on the top category, certificate automation before the shrinking-lifetime deadlines force it.
- **Large / regulated**: field-level protection and tokenization for the crown-jewel identifiers, custody-separated key architecture where regimes demand it, label-driven DLP in blocking mode on proven channels, crypto inventory feeding a PQC migration roadmap with dated milestones.
- Universal ordering: classification mechanism → discovery/data map → encryption-by-state with the key custody question answered → retention/deletion → DLP last, not first.

## Assessment questions

- Show me the data map: where does the most sensitive category live, and when was that inventory last refreshed by automated discovery rather than by asking around?
- What applies classification labels — people, templates, location inheritance, or nothing? Sample ten recent documents/objects and count the labeled ones.
- For the crown-jewel data store: which encryption layer protects it, against which adversary, and who can decrypt — enumerate the principals, including platform and KMS admins.
- What happens when a key is compromised — is there a documented, tested rotation/re-encryption path, or would it be a research project?
- What was deleted last quarter because retention said so, and can you evidence it?
- Is production data in non-production environments, and is the answer verified or assumed?
- What is the DLP program's alert volume, true-positive rate, and analyst cost per week — and who owns tuning?
- Does a cryptographic inventory exist, and what in it protects data that must stay confidential past ten years?
