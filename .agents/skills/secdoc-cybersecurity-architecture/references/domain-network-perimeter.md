# Network & Perimeter Security Architecture

## Scope

This domain covers the security policy and zone architecture of the network: trust boundaries and segmentation design, the policy layer above the enforcement devices, network detection, remote-access policy, and TLS inspection as a policy decision. Boundary sentences, load-bearing for this file: **device-level firewall/switch/router engineering — platform mechanics, feature configuration, hardening — composes with the network-engineering skill; SASE/SSE adoption strategy and WAN design compose with the networking-architecture skill; this file owns the security policy and zone architecture both of those implement.** Identity signals consumed at enforcement points come from `domain-iam.md`; the zero-trust reference model is SP 800-207 via `nist-sp.md`.

## Architecture patterns

**The multiplied perimeter, argued as architecture.** The perimeter didn't die — it multiplied. Cloud tenancy edges, SaaS boundaries, remote users, partner interconnects, OT zones, and the API surface are all perimeters now, each needing the same design questions the single firewall used to answer alone: what trust domains exist, where are their boundaries, and what enforces each one. The architecture failure mode is asymmetry — a hardened internet edge in front of a flat interior where one workstation compromise reaches everything. Perimeter thinking still applies; it applies *everywhere*, which is the zero-trust claim stated in network terms (`nist-sp.md`, 800-207 pitfall: an architecture pattern, not a product).

**Zones and trust boundaries.** Zone design starts from data classification and function, not from the existing VLAN map: define zones by what they protect (crown-jewel data stores, payment systems, user endpoints, guest, OT, management) and what trust each is granted; every inter-zone flow crosses an enforcement point with explicit policy; and the classically forgotten zones get drawn deliberately — the **management plane** (device management interfaces, hypervisor/console access, out-of-band — its own zone, reachable only from the privileged-access path in `domain-endpoint.md`/`domain-iam.md`), the **backup network** (ransomware's priority target — see the crown-jewel path tracing in `architecture-best-practices.md`), and OT (Purdue-model zoning, composing with the OT exception class in `domain-endpoint.md`). Cloud translation: zones become accounts/VPCs/VNets and security-group tiers — the account boundary is the strongest zone edge cloud offers (`domain-cloud-hybrid.md`).

**Segmentation and microsegmentation policy design.** The spectrum, chosen by blast-radius requirement against operational cost: coarse zone segmentation (network/firewall-enforced, the affordable default) → per-application segmentation (application tiers isolated, east-west policy between them) → microsegmentation (per-workload policy, host-based or fabric-enforced: identity-tagged rules following the workload rather than the IP). Microsegmentation's honest prerequisite is a **dependency map** — policy for flows you haven't mapped produces either outages (too tight) or theater (too loose); the discovery/monitor-mode phase *is* the project, and vendors selling six-week microsegmentation are selling monitor mode. Segmentation claims get validated by testing (attempted cross-zone flows, both directions) — PCI requires exactly this for CDE segmentation (`compliance.md`), and the discipline generalizes: a segment that's never been tested is a diagram.

**The policy layer above the devices.** What the rules should allow and why — the layer that outlives any vendor:
- **Rulebase governance** — every rule carries an owner, a business justification, and an expiry/review date; changes ride the change process with security review for risk-relevant modifications; and the rulebase is audited on a schedule for shadowed, redundant, and expired rules. The pathology is universal: rulebases only grow, "temporary" rules from 2019 persist, and any-any diagnostics become load-bearing. Recertification (rule owners re-justify on a cycle) is the counterweight — and it's evidence auditors accept (SOX operations, PCI Req. 1.2.7's periodic ruleset review).
- **Default-deny discipline** — deny as the base posture at every enforcement point, permits as the documented exception; assess by reading the *last* rule and the hit counts on broad permits. Outbound counts too: unrestricted egress is the exfiltration and C2 path, so egress policy (proxy-enforced categories, allowlisted destinations for servers — server subnets rarely need arbitrary internet) is where default-deny earns its keep, and its absence is a finding regardless of how strict inbound is (ATT&CK TA0011 Command and Control, TA0010 Exfiltration — `mitre-attack.md`).
- **East-west visibility** — you cannot govern flows you cannot see: flow telemetry (NetFlow/IPFIX/VPC flow logs) from the interior, not just the edge, feeding both the dependency mapping above and detection below. Most estates have edge visibility and interior blindness; the finding writes itself.

**NDR and network detection architecture.** Network detection remains the layer that sees what endpoint agents can't — unmanaged and OT devices, agent-tampered hosts, lateral movement between them (`domain-endpoint.md`'s coverage gap is NDR's value case). Architecture decisions: sensor placement by value (internet edge, data-center/cloud east-west aggregation points, the management and backup zones) rather than everywhere; encrypted-traffic reality stated plainly — without inspection (below), NDR works from flow metadata, JA3-class fingerprinting, and behavioral analysis, which is genuinely useful and genuinely less than payload inspection; and integration over console sprawl — NDR signal routes into the SIEM/SOC pipeline with everything else (`domain-secops.md`), and ATT&CK Data Source mapping tells you which techniques network telemetry is carrying detection weight for.

**Remote access policy architecture.** The design conversation is policy, not product: **ZTNA against SP 800-207** means per-application, identity-and-device-conditioned access (the PDP consuming `domain-iam.md` signals, the PEP brokering the connection) replacing the VPN's network-level grant — the security win is the death of "connected, therefore on the network." Policy design discipline: applications enumerated and access scoped per application/role (the enumeration is the project — ZTNA deployments stall on the app inventory, not the connector); device posture as a condition (`domain-endpoint.md` compliance signals); the unmanaged-device answer decided explicitly (browser-isolated access to named apps, or nothing); and the legacy tail (thick clients, arbitrary-port protocols, admin access to infrastructure) either kept on a shrinking, policy-tightened VPN or routed through the privileged-access path (`domain-iam.md` session brokering) — pretending the tail doesn't exist is how "we replaced the VPN" becomes two remote-access systems, one unwatched. Whether ZTNA arrives via SASE/SSE bundling is an adoption-strategy question for the networking-architecture skill; the policy architecture here is what any of those deployments must implement.

**TLS inspection as a policy decision.** Break-and-inspect is a *policy* choice with costs, not a default-on feature. State all three cost classes before recommending: **privacy/legal** — decrypting employee traffic touches monitoring-consent and works-council/jurisdictional constraints, and some categories (health, finance, legal) are commonly policy-exempted, so the bypass list is a governance artifact with an owner; **technical** — certificate pinning and mutual TLS break under interception (client bypass lists again), TLS 1.3 and encrypted client hello narrow midpath options, and the inspection device becomes a high-value target holding a trusted CA key (protect it at tier-0 standard — `domain-iam.md` custody logic applies); **operational** — capacity, latency, and the failure-mode decision (fail-open forfeits the control silently; fail-closed makes inspection an availability dependency — decide explicitly, per `architecture-best-practices.md` fail-secure). The honest scoping: inspect where detection value is highest (egress from server zones, download/upload paths), exempt where law or breakage demands, and document the residual blindness as accepted risk rather than ignoring it. Where inspection is declined, compensate with endpoint-side visibility (`domain-endpoint.md` — the EDR sees plaintext at the ends) and metadata-based NDR.

## Control mapping

- **SP 800-53 Rev. 5**: SC-7 (boundary protection — the domain's anchor, with enhancements: SC-7(5) default-deny, SC-7(11)/(12) restrict incoming/host-based protection, SC-7(21) isolation of system components), AC-4 (information flow enforcement — the policy layer's formal home), AC-17 (remote access), CA-9 (internal connections), SC-8 (transmission protection), CM-7 (least functionality applied to network services), SI-4(4)/(11) (inbound/outbound traffic monitoring).
- **CSF 2.0**: Protect (PR.IR-01 network protection, PR.AA-06 access decisions at enforcement points), Detect (DE.CM-01 network monitoring).
- **ATT&CK**: TA0008 Lateral Movement (what segmentation blunts), TA0011 Command and Control and TA0010 Exfiltration (what egress policy and NDR address), T1133 (External Remote Services — the VPN/remote-access attack surface ZTNA policy narrows), T1046 (Network Service Discovery — what default-deny interior policy starves); mitigations M1030 (Network Segmentation), M1037 (Filter Network Traffic); map per `mitre-attack.md`.
- **Compliance hooks**: PCI DSS Req. 1 (network security controls, 1.2.7 ruleset review, segmentation-testing requirements per the scoping guidance); CMMC/800-171 3.13 (System and Communications Protection — CUI enclave boundaries are this domain's pattern applied to scoping, see `compliance.md`); SOC 2 CC6.6; GDPR Art. 32 appropriate technical measures, with TLS-inspection privacy analysis feeding Art. 25/DPIA work where employee data is decrypted.

## Decision criteria

- **Small org**: coarse zones (user / server / guest / management), cloud account boundaries as the segmentation mechanism for cloud workloads, egress filtering via a SaaS proxy, ZTNA-style access from the IdP's app-proxy tier — no microsegmentation, no inspection farm; discipline over machinery.
- **Mid-size**: per-application segmentation for crown jewels, rulebase governance formalized with recertification, interior flow telemetry deployed, ZTNA for the workforce mainstream with the legacy VPN tail explicitly inventoried and shrinking, TLS inspection scoped to server-zone egress if the governance work is done.
- **Large / regulated**: microsegmentation where dependency mapping has matured (regulated enclaves first — CDE, CUI), NDR at east-west aggregation points, formal network-policy-as-code where fabric supports it, segmentation validation testing on a schedule, and the management/backup zones treated with tier-0 discipline.
- Universal ordering: draw the zones and flows → default-deny at the boundaries that exist → egress policy → visibility (flow telemetry) → then finer segmentation and inspection. Microsegmentation before dependency mapping is outage roulette.

## Assessment questions

- Show me the zone model: what zones exist, what does each protect, and where's the diagram of *flows between them* — not the topology, the flows?
- Read me the last rule at the internet edge and the interior enforcement points. What are the hit counts on the five broadest permits, and who owns each?
- What can a compromised user workstation reach — has anyone tested lateral movement from that segment, and when?
- What restricts outbound traffic from the server zones? If a server initiated a connection to an arbitrary internet host right now, what would stop or see it?
- What flow telemetry exists for east-west traffic, and does it reach the SOC (`domain-secops.md`) or a storage bucket nobody queries?
- How does remote access work for: a managed laptop, an unmanaged personal device, a third-party contractor, and an infrastructure admin? Which of those paths is a network-level grant?
- Is TLS inspected anywhere? Who approved the bypass list, when was it last reviewed, and what's the stated failure mode of the inspection path?
- What's on the management network, and what can reach it from the user LAN? (The correct answer is nothing.)
